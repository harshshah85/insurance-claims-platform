1. The Three Pillars + the Fourth

Metrics — what is happening right now?

Throughput per topic, consumer lag, processor latency, API latency/error rate, STP rate, payment success rate. Collected every 60s. Used for SLO burn-rate alerting and capacity planning.

Logs — why did it happen?

Structured JSON logs from intake, processors, APIs, correspondence, payment saga. Centralized; 90-day retention; no raw PII/PHI in logs (tokens only). Searched for root cause.

Traces — where did the request go?

Distributed tracing with correlationid propagated FNOL → API → processor → read model. Identifies latency hotspots across service and topic boundaries.

Event lineage — the fourth pillar

Unique to event sourcing: the correlationid/causationid chain lets you replay exactly how any decision or payment came to be. This is both an ops tool and the regulatory audit answer.

5. Incident Management

PhaseAction
DetectAutomated alert pages the on-call engineer; ack within 15 min (P1) / 30 min (P2)
TriageIncident channel; incident commander; blast radius (which claims/payees affected)
DiagnoseMetrics for anomaly start; logs by correlationid; trace the causal event chain
MitigateScale consumers, pause/resume processors, replay from offset, hold payments if money-movement is implicated
ResolveSLOs back to green; for any held payments, confirm no double-pay before release
Post-mortemBlameless, within 48h for P1s; 5-whys; action items tracked with owners
Replay is the superpower and the footgun: a projection bug is fixed by rebuilding the read model from the log — safe, because projections are derived. But replaying anything that triggers side effects (correspondence, payments) must run against idempotent consumers or with side effects disabled, or you re-send letters and re-pay beneficiaries. The platform marks side-effecting consumers explicitly so replays are scoped.
