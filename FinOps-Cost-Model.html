The honest headline: at this scale infrastructure isn't the expensive part — the build is. The Kafka and cloud run-rate is real but modest next to the engineering effort. So cost control is mostly scope discipline and not over-building ahead of need; the infra levers in §4 trim the run-rate at the margins. (For reference, the supporting-infrastructure run-rate in §1 lands in the order of a few thousand to low-five-figures per month at the volumes assumed.)

Framing: the platform pays back mainly through two levers — auto-ticketing clean claims (the biggest, and it compounds as the low-touch path widens) and faster cycle time (visible immediately, even before any automation). Ship the thin slice, prove cycle-time on real claims, and the case for going further makes itself.

4 FinOps Optimization Levers

1 · Topic retention & tiered storage — Keep the event-sourced log (claims.lifecycle) on long retention with tiered storage so its full history stays replayable (never compacted); compact only the latest-state topics (policy.snapshot, party.identity); and time-bound high-volume delete topics (claims.fnol 7d). Archive closed-claim history to cheap object storage for the statutory retention period.
2 · Kafka tiered storage — Move older segments off broker disk to object storage; large reduction on long-retention cost without losing replay.
3 · Right-size stream parallelism — Decisioning and fraud are the compute-heavy processors; low-volume projectors don't need the same parallelism. Tune per processor, review quarterly.
4 · API-gateway caching — Cache GET /claims/{id} with a short TTL aligned to projection lag; cuts read-model query load for repeat status checks (clients refresh the same claim repeatedly).
5 · Autoscale on consumer lag — Scale processor replicas on lag, not a fixed schedule; scale to zero for batch-like jobs (DI monthly benefit run) between runs.
6 · Observability hygiene — 90-day log retention, trace sampling, metric filters instead of logging raw payloads. Observability is often the second-largest line after Kafka — keep it deliberate.
7 · Defer ML until the data earns it — ML compute and a feature store are real cost. Rule-based decisioning/fraud carries the early stages with no training-data spend and full explainability; ML earns its cost only once there's enough labeled history to train on.
8 · Spend LLM inference only where it pays — The agent assist layer is genuine per-token cost. Gate it to the tiers where a human is in the loop (skip the deterministic auto-ticket lane), triage with a smaller/cheaper model and escalate to a larger one only when needed, cap the context window, and cache deterministic lookups (policy/coverage) instead of re-prompting. Inference scales with claim volume, so right-sizing the per-claim token budget is the lever.
