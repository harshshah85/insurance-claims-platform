Event Streaming Architecture

Topic design, event contracts & stream topology — the Kafka backbone that carries every claim from filing to payment.

Prepared by Harsh Shah  |  June 2026
The idea in one line: Kafka isn't a side-channel here — it's the backbone. Each claim is stored as its ordered list of events, and that list is the official record. Everything else — auto-ticketing, fraud checks, letters, payments, reporting — simply reads from it. This document follows the events from the ground up: the facts themselves, the topics that carry them, the contract they share, how they form the record, and how they're processed reliably.

1 The Domain Event Catalog — 36 Events

Start with the facts. Events are immutable, named in the past tense, and grouped by the bounded context that owns (produces) them — everything downstream is built from these.

Agentic decisioning events are recommendations by design. The agent workers emit their own events on claims.ai.v1 — e.g. DecisionProposed, EscalatedToManualReview — as recommendations and hand-offs, distinct from the 36-event catalog of authoritative facts. Those facts (ClaimApproved, ClaimDenied, ClaimAutoApproved) stay owned by the Adjudication context and are produced by a human decision or the deterministic auto-ticket lane — agents reason, people decide. (See AI-Assisted & Agentic Decisioning.)

Why claim_id keying matters: partitioning on claim_id guarantees per-claim ordering — every event for one claim lands on one partition and is processed in sequence. This is what makes the event-sourced aggregate deterministic. Cross-claim ordering is never assumed.
Cleanup policy follows the topic's role. The event-sourced log and the fact / audit streams (claims.lifecycle, claims.decision, di.benefit, payment.disbursement) use time/size retention on tiered storage — the full history has to stay replayable, so they are never compacted. Compaction is reserved for latest-state topics — policy.snapshot.v1 (current policy state per policy_id) and party.identity.v1 (current verified identity per party_id) — where only the newest value per key matters. Compacting an append-only log would silently discard the very history event sourcing depends on.

Agentic decisioning topic — a derived advisory stream

The agent workers publish their analysis and recommendations to a dedicated topic. By design it is a derived stream — separate from the system-of-record topics the same way CQRS read models are derived from the log — so the canonical decision still lands on claims.decision.v1, signed by a human (or by the rules on the auto-ticket lane). It sits alongside the 14 core topics rather than inside them, by intent.

TopicClassKeyPartitionsRetention / CleanupPurpose
claims.ai.v1Event (advisory)claim_id1290d deleteLLM analysis, proposed decision packets (rationale + citations + confidence), and escalation/abstention events. Consumed by adjudicator worklists; never auto-decides or moves money.

3 Event Contracts & Schema Evolution

An event is a contract: a shared envelope wrapping a versioned Avro payload, governed by a Schema Registry. Getting the contract right is what lets dozens of independent consumers read the same stream for years without breaking.

Canonical event envelope

Every event shares a CloudEvents-style envelope so consumers, the DLQ, and the audit store can treat all 36 event types uniformly. The domain payload is nested under data.

// envelope is identical across all 36 event types
{
  "id": "01HZX9...ULID",                // globally unique, sortable
  "type": "claims.decision.ClaimAutoApproved",
  "source": "svc-decisioning",
  "subject": "CLM-2026-018342",             // claim_id (partition key)
  "time": "2026-06-03T14:22:07Z",
  "specversion": "1.0",
  "schemaversion": "v1",
  "correlationid": "01HZX1...ULID",         // the originating FNOL event id
  "causationid": "01HZX8...ULID",            // the event that caused this one
  "data": { /* typed Avro domain payload */ }
}
Correlation vs. causation: correlationid stays constant for the whole claim journey (traceability); causationid points at the immediate predecessor event. Together they let you reconstruct the exact causal chain of a decision — essential for a regulator or a disputed denial.

Avro on the wire, governed by compatibility rules

The payload under data is Avro, registered in a Schema Registry that enforces compatibility per topic group — so a schema change can't silently break the consumers reading historical events.

Topic GroupCompatibility ModeRationale
Event (fact) topicsBACKWARD_TRANSITIVENew consumers must read all historical events. Producers may add optional fields; never remove or repurpose a field.
Command topicsFORWARDOld producers must keep working as the handler evolves; the consumer (handler) is upgraded first.
CDC topics (policy.snapshot)BACKWARDSource schema is owned by Policy Admin; downstream absorbs additive change.
One topic, many event types. Several topics carry more than one event type — claims.decision.v1 alone carries approved / denied / pended / reversed. The registry therefore uses TopicRecordNameStrategy, where the subject is <topic>-<RecordName>, so each event type evolves under its own schema while sharing the topic — not the default TopicNameStrategy (one schema per topic), which can't model a multi-type stream.

Evolution rules (enforced in CI, not by convention)

  • Adding a field requires a default — older consumers read the default.
  • Removing or renaming a field is forbidden in v1; it forces a new .v2 topic and a dual-write migration window.
  • Enum values are append-only; consumers handle an UNKNOWN default for forward safety.
  • The build fails if a producer publishes a schema the registry rejects — schema breakage cannot reach production.

4 Event Sourcing & CQRS

The event log is the source of truth; everything readable is a projection built from it.

Write side — the aggregate

The Claim aggregate is rehydrated by replaying its events from claims.lifecycle.v1 — a retention-based (non-compacted) log keyed by claim_id, held on tiered storage so the full event history stays replayable. A command handler validates an incoming command against the rehydrated state, then appends new events. No in-place mutation ever occurs.

Snapshots bound replay cost. Replaying from offset 0 on every load doesn't scale, so the aggregate is snapshotted periodically — Kafka Streams backs it with a compacted changelog / state store (latest state per claim_id). Rehydration restores the latest snapshot and replays only the events since it; a full cold rebuild still replays the whole log. This compacted changelog is the one place compaction fits the write model — exactly because it holds latest-state, not history.
# Command path (write side) cmd.adjudicate.v1 ─► Command Handler ─► rehydrate Claim from claims.lifecycle.v1 │ ├─ validate invariant (e.g. cannot approve a contestable claim w/o review) └─ append StpEligibilityScored → ClaimAutoApproved to claims.lifecycle.v1 # Query path (read side) — built by stream processors, never by the writer claims.lifecycle.v1 ─► Projector (Kafka Streams) ─► claim_summary read model (relational store) └─► advisor_worklist read model (search index)

Rebuild safety: because read models are pure projections, any one can be dropped and rebuilt by replaying the log from offset 0. This is the operational escape hatch — a projection bug is fixed by deploying the corrected projector and replaying, not by data-patching production rows.

5 Delivery Guarantees & the Outbox

Once the record and its read models are in place, the wiring between them has to be exactly-once where it counts.

Exactly-once where it matters

Stream processors that both read and write Kafka (decisioning, fraud scoring, projections) run with EOS — processing.guarantee=exactly_once_v2 — so a consume→transform→produce cycle is atomic. Idempotent producers + transactional writes prevent duplicates on retry.

Transactional outbox for the edges

Where the platform must change a relational store and emit an event (e.g. intake writing a claim row and emitting FnolCaptured), it never dual-writes. It writes the event to an outbox table in the same DB transaction; a Kafka Connect outbox connector tails it. This removes the “DB committed but Kafka publish failed” failure mode.

# Outbox pattern — no distributed transaction, no lost events Intake Service ─► BEGIN TX INSERT claim row INSERT outbox(event=FnolCaptured) COMMIT TX │ Kafka Connect (CDC) ◄┘ ─► publish to claims.fnol.v1 ─► delete/mark outbox row

Poison-message handling

A consumer that cannot process an event retries with backoff via the tiered retry topics (claims.retry.1m/5m/30m). After the final tier it lands in claims.dlq.v1 with failure headers (x-exception, x-original-topic, x-retry-count). The DLQ is monitored (see Observability) and drained by an operator tool, never auto-replayed blindly.

Resilience by design — agents reason off the committed log. The agent workers consume committed facts and publish advisory output to claims.ai.v1; because they don't mutate the system of record, they run independently of the exactly-once decisioning/fraud/projection transactions. The payoff is deliberate: a slow or failed agent degrades adjudicator assist but can never corrupt or block a claim's authoritative history.
Why a join needs co-partitioning: the STP processor enriches a claim from three streams — claim events (claim_id), the policy snapshot (policy_id), and party identity (party_id). A Kafka Streams join requires every input co-partitioned on the join key, so the claim stream is re-keyed through repartition topics — to policy_id for the policy KTable join, and to party_id for the identity KTable join, then back to claim_id to emit the decision. These are deliberate, documented hops rather than accidental shuffles.

7 What Stays Off Kafka

The backbone has deliberate boundaries — it is not a document store and not a money-mover of record.

  • Large documents (death certificates, medical records, attending-physician statements) live in the ECM/object store; events carry a reference and hash, not the binary.
  • The actual debit/credit happens in the treasury/disbursement platform; Kafka carries the command and the settled fact, and the platform reconciles — Kafka is not the ledger of record for cash.
  • PII minimization: SSNs and medical detail are tokenized; the event carries a token, and the vault resolves it under access control (see Security & Regulatory Compliance).
